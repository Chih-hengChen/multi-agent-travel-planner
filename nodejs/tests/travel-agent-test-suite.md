# Multi-Agent Travel Planner 测试集 (v1.0)

本测试集用于验证多智能体旅行规划系统在不同地理跨度、交通复杂度及预算约束下的表现。重点测试 `Transport MCP` 的调度、`Map MCP` 的空间感知以及 `BudgetLoopController` 的回退逻辑。

## 1. 大城市 ⇄ 大城市 (Large-to-Large)

**核心测试点**：海量数据下的过滤能力、同城复杂交通（地铁/打车对比）、高密度日程编排。

### 测试用例 1.1：极致性价比的周末特种兵

- **输入**：“这周五晚从上海去北京，周日晚回。预算 1500，越省越好，主要想看故宫和升旗。”
- **预设画像/参数**：`budget_strictness: strict`, `transport_preference: no_preference`
- **预期 Pipeline 行为**：
  - **Transport Agent**: 必须对比周五晚的高铁和红眼航班。由于预算极低，应优先推荐硬卧/高铁二等座或廉航，并准确计算凌晨到达的附加交通成本。
  - **Hotel Agent**: 过滤掉常规酒店，搜索天安门/前门附近具备“青旅”或“太空舱”标签的低价住宿，保证 `alternatives` 数组中包含步行可达天安门广场的选项。
  - **Activity Agent**: 识别“升旗”的时间敏感性，利用 Map MCP 将周六凌晨的行程时间精确到分钟，并串联故宫。
- **最终输出断言**：总费用 ≤ 1500，必须包含明确的夜间/凌晨市内交通方案（如夜班公交或打车预估）。

### 测试用例 1.2：商务差旅转休闲

- **输入**：“下个月 5 号到 8 号，广州到成都。预算 8000，想要住得舒服点，吃点正宗的，不要太累。”
- **预设画像/参数**：`budget_strictness: luxury`, `interests: ["food", "relaxation"]`
- **预期 Pipeline 行为**：
  - **BudgetAgent**: 识别到预算充足，不触发削减回滚策略（`ADJUSTING`）。
  - **Hotel Agent**: 主选五星级/豪华型酒店，备选需突出“餐饮服务好”或“SPA体验”。
  - **Activity Agent**: 每日活动数需自动减少（如从 3 个降至 1-2 个），安排下午茶或足疗，增加餐饮开销的比重。

## 2. 大城市 ⇄ 小城市 (Large-to-Small)

**核心测试点**：长途大交通与区域小交通的衔接、下沉市场酒店数据的回退策略。

### 测试用例 2.1：高铁换乘与特色民宿

- **输入**：“武汉出发去江西景德镇，玩 3 天。喜欢陶瓷文化和逛集市，预算 3000。”
- **预期 Pipeline 行为**：
  - **Transport Agent**: 识别直达高铁频次。若无合适直达，需利用 MCP 查询“武汉-九江/南昌-景德镇”的换乘方案。
  - **Hotel Agent**: 放弃大型连锁酒店的数据池，按标签检索“民宿”、“客栈”，主备选需对比“陶溪川附近（方便逛夜市）”与“三宝村（贴近自然）”。
  - **Activity Agent**: 强绑定 `history/museum` 意图，串联中国陶瓷博物馆、御窑厂、陶溪川周末集市。
- **最终输出断言**：交通方案必须无缝衔接，市内交通提示由于小城市公共交通可能不发达，建议打车或租电动车，并给出预估单价。

---

## 3. 小城市 ⇄ 小城市 (Small-to-Small)

**核心测试点**：极端交通条件下的兜底逻辑（缺乏航线/高铁）、空间距离补偿。

### 测试用例 3.1：滇西无轨道交通接驳

- **输入**：“我在云南大理，后天想去腾冲泡温泉，去 2 天 1 夜就回，预算 2000。”
- **预期 Pipeline 行为**：
  - **Transport Agent**: Map MCP 和 Transport MCP 联合探测，发现无直达高铁和商业航班。必须触发回退机制（Fallback），推荐长途大巴（大理汽车客运站）或网约车拼车/包车，并给出耗时预估（约 4-5 小时）。
  - **Activity Agent**: 考虑到单程耗时半天，第一天必须安排在下午/晚上（温泉），第二天上午安排周边短途游（如和顺古镇），下午返程。
- **最终输出断言**：明确警告没有高铁/飞机直达；行程表中必须预留充足的在途时间。

---

## 4. 多个旅游地之间 (Multi-Destination / Loop)

**核心测试点**：动态锚点推移（每日酒店不同）、包车/租车成本均摊、超长链路的 Context 管理。

### 测试用例 4.1：青甘大环线经典 6 日游

- **输入**：“我们 2 个人，想从西宁出发走青甘大环线（经过青海湖、茶卡、大柴旦、敦煌、张掖最后回西宁），一共 6 天，总预算 12000。”
- **预期 Pipeline 行为**：
  - **State Machine (核心挑战)**: 必须从静态的 `DestinationAgent` 升级为 `RoutingAgent`。将 6 天拆分为 6 个子状态，每天的 `departure_city` 和 `destination` 都在滚动更新。
  - **Transport Agent**: 识别出这是公路旅行路线。废弃火车/飞机，全局推荐“租车自驾”或“包车”，并将交通总成本（如 3000 元/车）均摊到总预算中。
  - **Hotel Agent**: 每天需根据当晚的落脚点（如：Day 1 黑马河，Day 2 大柴旦，Day 3 敦煌）检索对应的酒店。
  - **Activity Agent**: 沿途景点的线性串联（Map MCP 必须校验景点的顺路程度，避免折返跑）。
- **最终输出断言**：
  - 输出中必须明确这是一条**环线自驾/包车**方案。
  - 包含每天的行驶里程和预估驾驶时间（如：西宁 -> 青海湖 150km，约 2.5 小时）。
  - 住宿列表必须是一个长度为 5 的数组，分布在环线沿途的不同城镇。
